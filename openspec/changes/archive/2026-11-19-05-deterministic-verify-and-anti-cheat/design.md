# Design

## Context

SpecLearn now has COURSE-SPEC loading, active course state, sandbox isolation, and `/slx:*` skill templates. The remaining trust boundary is deterministic module verification. See `proposal.md` for motivation and scope.

## Goals / Non-Goals

**Goals:**
- Execute each module's declared test command locally and capture structured process results.
- Lock declared test files and detect deletion, emptiness, or SHA-256 mismatch.
- Produce deterministic completion evidence that the progress model accepts only from successful verification.
- Unlock prerequisite-valid downstream modules only after verification evidence exists.
- Integrate `/slx:verify` with Socratic failure guidance and rubric review.

**Non-Goals:**
- Add remote or cloud test execution.
- Allow a student or agent to generate verification signatures manually.
- Execute tests as part of course start or lock-tests.
- Replace the course rubric with automated natural-language grading.
- Store secrets or authentication data in progress state.

## Decisions

- **Use Node.js native subprocess execution:** `src/commands/verify.ts` will invoke the module's `test_command` locally and capture exit code, stdout, and stderr. Command parsing should use a shell only when required by platform syntax, and verification must remain deterministic enough to reproduce the signature inputs.
- **Resolve the active module explicitly:** `verify [module-id]` will prefer the supplied module; without an argument it will use the active course's current module or the first available/in-progress module according to a documented, deterministic rule.
- **Lock test files at module start or lock-tests:** `src/security/integrity.ts` will read each declared `test_files` path relative to the project or sandbox root, reject missing or empty files, and store `{path: sha256}` evidence in progress state.
- **Use canonical SHA-256 text:** Hashes will represent the exact bytes of each test file. Verification will reject missing files and zero-byte files and compare canonical path keys relative to the project root.
- **Generate a verification signature:** The signature will be a SHA-256 digest of canonical `courseId + moduleId + test_command + exitCode(0)`. It is evidence of a successful CLI verification run, not a cryptographic secret or remote attestation.
- **Require signature and integrity checks together:** Completion and downstream unlocking occur only when subprocess exit code equals zero, all locked test hashes match, and the signature is generated by `verify` in the same run.
- **Preserve failure state:** Non-zero exit code, process launch failure, missing tests, or hash mismatch will leave module completion and downstream availability unchanged. Output is retained for the Socratic review skill.
- **Keep rubric review agent-facing:** The CLI will return rubric checks and git diff context separately. `/slx:verify` will analyze the diff and ask one final conceptual question after tests pass.
- **Validate direct progress edits conservatively:** Progress state will require completion evidence fields and reject module completion if the signature or hash evidence is absent or malformed.

## Risks / Trade-offs

- **Test command shell portability** → Use platform-aware subprocess options and document shell semantics; capture launch failures clearly.
- **Test files without assertion-bearing content** → Locking will reject zero-byte files but cannot prove that a non-empty file contains meaningful assertions; rubric review remains the secondary human/agent check.
- **Signature forgery by local editing** → The signature prevents accidental or direct progress edits but does not provide a cryptographic secret against an adversary controlling the local machine. The scope is anti-cheat for agent and state-file mistakes, not hostile local root control.
- **Test-file regeneration** → A declared file can be restored to a previous hash if a student has a malicious local copy; locking establishes an integrity baseline and should be recorded before module work begins.
- **DAG unlocking ambiguity** → Only prerequisites satisfied by `completed` or `skipped_mastered` nodes will unlock downstream modules; this keeps the existing state model consistent.

## Migration Plan

Existing progress state will remain readable. Modules without locked test hashes or verification signatures may be initialized with no completion evidence. A legacy `completed` status will not be treated as a successful new verification unless evidence is present. Existing `/slx:verify` templates may be regenerated from the adapter managed section.

## Open Questions

None. The verification command, integrity baseline, signature inputs, and completion boundary are sufficiently defined for implementation.
